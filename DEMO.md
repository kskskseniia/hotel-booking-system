# Демонстрационные данные

Профиль Spring `demo` добавляет начальные данные только в `booking-service` и
`hotel-service`. Без этого профиля тестовые аккаунты, отели и номера не создаются.

## Учётные записи

| Роль | Логин | Пароль |
|---|---|---|
| USER | `demo-user` | `DemoUser123!` |
| ADMIN | `demo-admin` | `DemoAdmin123!` |

В базе пароли хранятся как BCrypt-хеши.

## Отели и номера

| Отель | Номер | Доступен | Число бронирований |
|---|---:|---:|---:|
| Москва | 101 | да | 0 |
| Москва | 102 | да | 2 |
| Москва | 103 | нет | 0 |
| Санкт-Петербург | 101 | да | 1 |
| Санкт-Петербург | 102 | да | 3 |

Номера комнат могут повторяться в разных отелях, поэтому `101` и `102` есть в
обоих. Такой набор показывает фильтрацию недоступных номеров и сортировку
рекомендаций по возрастанию числа бронирований.

## Как взаимодействуют сервисы

```text
Клиент / Swagger -> API Gateway -> Booking Service
                              `-> Hotel Service

Booking Service -------------> Hotel Service
              выбор, подтверждение и освобождение номера
```

- **API Gateway** принимает внешние запросы и направляет их в нужный сервис.
- **Eureka Server** хранит адреса запущенных сервисов, чтобы Gateway и сервисы
  находили друг друга без жёстко заданных адресов.
- **Booking Service** регистрирует пользователей, выдаёт JWT и хранит историю
  бронирований. При создании или отмене брони он обращается в Hotel Service.
- **Hotel Service** хранит отели, номера и закрепления номеров за бронями. Сам к
  Booking Service он не обращается.

Создание брони проходит кратко так:

1. Клиент отправляет запрос через Gateway в Booking Service.
2. Booking Service проверяет `requestId` и создаёт бронь `PENDING`.
3. При `autoSelect=true` он запрашивает рекомендации у Hotel Service; иначе
   использует переданный `roomId`.
4. Hotel Service проверяет даты и закрепляет номер за бронью.
5. При успехе бронь становится `CONFIRMED`, при недоступном номере —
   `CANCELLED`. Временные межсервисные сбои обрабатывает фоновое восстановление.
6. При отмене Booking Service просит Hotel Service освободить номер и сохраняет
   бронь в истории со статусом `CANCELLED`.

## Формат ошибок

Booking Service, Hotel Service и собственные ошибки API Gateway возвращают один
JSON-формат:

```json
{
  "timestamp": "2026-11-17T20:00:00Z",
  "status": 409,
  "error": "Conflict",
  "message": "Username already exists",
  "path": "/user/register"
}
```

- `timestamp` — время возникновения ошибки в UTC;
- `status` и `error` — код и стандартное название HTTP-статуса;
- `message` — безопасное описание без паролей и внутренних деталей;
- `path` — путь исходного запроса.

Swagger обоих бизнес-сервисов показывает эту модель как `ErrorResponse` для
документированных ответов `4xx` и `5xx`.

## Запуск в VS Code / PowerShell

Перед первым запуском создайте локальный файл окружения из безопасного шаблона:

```powershell
Copy-Item .env.example .env.local
```

Откройте `.env.local` и замените все placeholders: укажите путь к JDK 21,
случайный `JWT_SECRET` длиной не менее 32 байт и данные bootstrap-администратора.
Файл `.env.local` содержит локальные секреты, уже исключён из Git и не должен
попадать в коммиты.

После однократной настройки Eureka Server и API Gateway запускаются как обычно,
а для двух бизнес-сервисов передаётся ключ `-Demo`:

```powershell
.\run-service.ps1 eureka-server
.\run-service.ps1 hotel-service -Demo
.\run-service.ps1 booking-service -Demo
.\run-service.ps1 api-gateway
```

Каждая команда запускается в отдельном терминале PowerShell. Ключ `-Demo`
включает профиль `demo` только в процессе соответствующего бизнес-сервиса.
После первоначальной настройки повторно изменять `.env.local` или глобальное
окружение для включения demo-профиля не требуется.
